PTB: Why nOAuth Is Not an Edge Case

Abdalrahman Mohamed · NEXUS Zone Research · 2026-10-21 · github.com/61465/identity-trust-hunt

Six vendors in seven days

On 2026-10-14 I filed two CVSS 9.8 critical advisories against Supabase and Hanko for the same underlying bug: a Microsoft Azure OIDC consumer that reads the email claim without checking xms_edov. Both were accepted. Seven days later, running a scanner I had just written against the same contract class, I filed two more advisories (Documenso Critical, Auth.js High) and emailed two more vendors (Keycloak, Casdoor). Keycloak's Response Team acknowledged within hours. Six vendors, one bug class, one week.

The 2024 writeup by Descope named this instance nOAuth. The reaction most writeups since have carried is “this is a specific Microsoft Entra misconfiguration, patch and move on.” This essay argues the opposite: nOAuth is one row in a class, the class spans every social-login provider shipping today, and the class has a static predicate you can scan for.

What nOAuth actually is

Microsoft Entra ID issues an email_verified claim on OIDC tokens. The claim reflects whether the token's home tenant considers that email verified. An attacker who creates a free Entra tenant is the home tenant for every user they add there. They can set mail to any address they want, mark it verified inside their tenant, and the resulting token carries email_verified: true that any consumer-side guard will trust.

Microsoft published xms_edov (Email Domain Owner Verified) as the distinguishing signal. xms_edov == "1" is set only when Microsoft itself has verified that the email's domain belongs to the token's tenant. It is the authoritative email-ownership claim for the Microsoft identity ecosystem. Not using it is the entire bug.

The pattern on the consumer side is one line of code:

const email = claims.email;              // trusts home-tenant verification only
if (!claims.email_verified) throw ...;   // insufficient guard
await linkOrCreateAccount({ email });    // attacker-controlled identity binding

Supabase, Hanko, Documenso, and Keycloak all shipped this shape. Casdoor shipped a variant where a generic isGothEmailVerified() helper applied the same insufficient check across every provider the markbates/goth library covers. Auth.js shipped a different adjacent instance: the GitHub provider trusts primary: true on /user/emails without checking verified: true.

From a specific bug to a framework

Finding the Microsoft case twice at Supabase and Hanko in one day told me the bug had an ancestor. Finding it again at four more vendors told me the ancestor had a class. The class is what I'm calling the Provider Trust Boundary:

For a call site c in system W that reads claim k from identity provider p, let V(p, k) be the set of verification steps the provider's semantic contract requires. Then c is PTB-unsafe iff some v in V(p, k) is absent from the enclosing scope of c.

In plain English: every identity provider publishes a contract — often buried in a reference page nobody rereads — for how a consumer must guard each claim. nOAuth is the Microsoft/email row of that contract going unenforced. There are many other rows.

Why static scanning works

PTB consumers read a claim at a specific call site. The guard is either on that call site, in the enclosing function, or in the surrounding file. A text-level scanner can walk a codebase, find the access patterns for claims.email / profile.mail / GET /user/emails, and check whether the required guard pattern appears in reach. Nothing in that loop requires AST parsing, nothing requires execution, nothing requires an LLM. v0.1 is 500 lines of Python, 24 passing tests, zero runtime dependencies.

Where static scanning stops being enough: taint-flow across modules (handler reads claim, calls a helper, helper is in another file, guard lives yet elsewhere); arrow-function predicates where the guard must live inline (.find((e) => e.primary && e.verified)); and operator-configured flows where whether a guard runs depends on realm settings not source code (Keycloak's first-broker-login customization). Those are the v0.2 roadmap, retained from the public edition because recall improvement is the researcher's edge, not the audience's.

What v0.1 catches it catches well: five of the six 2026-10-21 vendor findings started as a scanner hit, including a case (Documenso) that didn't appear in any of my prior manual recon notes. The scanner is the methodology's typing surface. The methodology is older than the scanner.

Four case studies

Supabase (GHSA-ffp4-94w6-vfgv, CVSS 9.8, accepted 2026-10-14). The IsEmailVerified() helper in api/provider/microsoft.go checked email_verified only. The repository's Microsoft OIDC adapter targeted the common tenant endpoint by default. Together they shipped the nOAuth bug class in production. Fix landed in a two-line consumer-side xms_edov guard.

Hanko (GHSA-2gvh-5vh3-m2rp, CVSS 9.8, accepted 2026-10-14). Worse than Supabase: the Hanko adapter hard-set emailVerified = true without checking any claim at all. The code path was reachable through the exact same attacker-tenant OIDC flow. Same two-line fix shape.

Documenso (GHSA-hm26-jm32-3wp4, Critical, filed 2026-10-21, under triage). Found by the scanner. packages/auth/server/lib/utils/handle-oauth-callback-url.ts reads claims.mail after checking email_verified only; MicrosoftAuthOptions targets login.microsoftonline.com/common. The scanner matched the Microsoft Graph mail read against an absent xms_edov guard anywhere under packages/auth/. Manual verification confirmed the attack path before the GHSA shipped.

Auth.js (GHSA-x3fc-mfpw-93f6, High, filed 2026-10-21, under triage). Different provider, same class. packages/core/src/providers/github.ts:171 reads (emails.find((e) => e.primary) ?? emails[0]).email. GitHub's /user/emails returns every email on the account including unverified secondaries. The find predicate gates on primary alone; verified is in the type definition and simply unused. A separate reporter already filed #13495 for the crash variant three months earlier; the PTB angle connects it to the Microsoft family.

Keycloak and Casdoor — email channels

Two vendors in the 2026-10-21 batch have GitHub private vulnerability reporting disabled. For Keycloak the correct channel is keycloak-security@googlegroups.com; for Casdoor it is admin@casdoor.org. Both reports went by email. Keycloak's Response Team acknowledged within 29 minutes and asked for credit attribution. A later reply pushed back on the severity — the default first-broker-login flow does ask the real account owner to verify ownership, so direct takeover of an existing user is blocked. The counter is that the idp-create-user-if-unique authenticator runs before that verification subflow in the default flow, and it creates a brand-new Keycloak user from an attacker-tenant Microsoft identity without any email challenge. The target is the unregistered email, not the existing user. Keycloak's architecture puts a 1:N multiplier on top of the base nOAuth bug because every downstream relying party of a Keycloak realm inherits the trusted email.

What this means for identity vendors

Three things, in increasing cost to implement.

Audit your Microsoft OIDC adapter for xms_edov, today. Grep xms_edov across your repository. If it does not appear in the file that extracts the email claim from a Microsoft token, you have the nOAuth bug class. The fix is one conditional in one function. The CVSS cost of shipping without it starts at 9.4 and goes up when a broker-chain multiplier is in play.

Walk the eight-row table. For each row your product consumes, locate the call site, locate the guard, and record either (a) “guard is reachable from the call site under all flows” or (b) “the guard is not applied here — filing issue”. The scan takes a day. For vendors with public source trees, identity-trust-hunt scan will do most of the grep automatically and will not false-positive on documentation strings.

Treat each new social-login provider as a new row of V(p, k). When you add a provider, do not import its SDK and assume the SDK's defaults are safe. Read the provider's token reference, pick the claim your account layer trusts, locate the authoritative verification signal for that claim, and encode the required guard as a type-level invariant where you can. The time cost is an afternoon per provider. The reputational cost of a CVSS 9.8 that cites your product by name is substantially higher than one afternoon of senior engineering time.

nOAuth is not an edge case. It is one row of a predicate class we now have the vocabulary to name, the dictionary to enumerate, and the tool to scan for.
